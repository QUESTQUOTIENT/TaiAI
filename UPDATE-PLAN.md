## 0. New findings since the audit

Investigating the plan surfaced **three things the audit did not catch**. They change the priority order, so they lead.

### 🔴 N1 — `pip-audit` has never actually scanned anything

The audit noted pip-audit was red. The cause is not a CVE — **the workflow command is invalid and exits before scanning.** Reproduced locally:

```
ERROR: the --disable-pip flag can only be used with a hashed requirements
       file or if the --no-deps flag has been provided
```

`.github/workflows/pip-audit.yml` runs `--requirement requirements.lock --strict --disable-pip`. The comment directly above it says *"`--no-deps`: only audit the project's direct deps"* — **but `--no-deps` was never put in the command.** `requirements.lock` has **0 hashes** (123 pins, no `sha256`), so `--disable-pip` is illegal without it.

The 15-second run times in the CI history are the tell: it fails on arg parsing, not on scanning.

### 🔴 N2 — 26 real vulnerabilities across 4 packages, including the one pypdf was pinned to fix

With the flag corrected, the scan actually runs:

```
Found 26 known vulnerabilities in 4 packages
Name               Version  ID                   Fix
pillow             12.2.0   PYSEC-2026-2253/…    12.3.0   (20 advisories)
mcp                1.27.2   PYSEC-2026-3483      1.28.1
pydantic-settings  2.14.1   GHSA-4xgf-cpjx-pc3j  2.14.2
pypdf              6.13.3   CVE-2026-59935/6/7/8 6.14.2
```

The irony worth flagging: `requirements.txt` pins `pypdf>=6.13.3  # GHSA-jm82-fx9c-mx94 fixed in 6.13.3; pip-audit-enforced`. It is **not** pip-audit-enforced — the enforcement was broken — and 6.13.3 has since collected **4 new CVEs**. `pillow` arrives transitively via `qrcode[pil]` (2FA QR codes).

**Dependabot PR #4 already fixes 3 of the 4** (`pypdf>=6.14.2`, `pydantic-settings>=2.14.2`, `pydantic>=2.13.4`). It has sat open since 2026-07-04 with CI **skipped**.

### 🔴 N3 — `requirements.lock` is not installable on Linux

```
ERROR: Could not find a version that satisfies the requirement pywin32==312
ERROR: No matching distribution found for pywin32==312
```

The lockfile pins `pywin32==312` with **no environment marker** — `grep -c ";" requirements.lock` returns **0**, so not a single one of the 123 pins is platform-gated. The lock was generated by `pip freeze` on the author's Windows box (consistent with the `D:/tieai-py-dev` paths in `evidence/`). Any Linux/macOS user or CI job doing `pip install -r requirements.lock` fails outright.

This also means **N1's fix alone is insufficient** — pip-audit still can't resolve the file until `pywin32` is marked.

### Why the four Dependabot PRs are all "skipped"

`ci.yml` triggers on `pull_request`. Dependabot PRs run under `pull_request_target`, which never matches, so **every check reports "skipped" and the PRs are unmergeable-by-policy but green-looking.** This is the same root cause as the audit's §4: CI is not gating.

## Phase 4 — First-run experience (P1, ~3 days)

The audit's key UX insight: **Tier 2 features are complete but unprovisioned, and a new user can't tell that apart from broken.** On a bare install they see `VectorRAG init failed`, `MemoryVectorStore DEGRADED`, `Discovered 0 model endpoints`, and empty arrays everywhere.

The codebase already contains the fix pattern. The Browser-MCP message is exemplary:

```
Built-in: Browser is not available.
  Reason: npm package '@playwright/mcp@latest' is not installed in the npx cache.
  Impact: tools provided by this MCP server will be unavailable.
  Fix:    npx -y @playwright/mcp@latest --version
          (run once, then restart TaiAi)
  Notes:  this server is optional; see README.md
```

## Sequencing

```
Phase 1 (1d)  ── gates live ──┐
Phase 2 (½d)  ── CVEs cleared ┤ ← both need Phase 1's CI to verify safely
Phase 3 (2d)  ── suite trusted┘
Phase 4 (3d)  ── first-run UX  ← highest product leverage
Phase 5 (½d)  ── hygiene       ← parallelizable, no dependencies
Phase 6 (∞)   ── structural    ← continuous
```

**Critical path: Phases 1→2→3, about 3.5 days**, and that is what converts the repo from "no effective gate" to "protected".

Phases 1 and 5 are safe to parallelize. Phase 2 should **not** start before 1.3/1.4, or you can't verify the CVEs are actually gone.

## Definition of done for the critical path

- [ ] `python -m pytest -q` runs clean from a fresh clone — no INTERNALERROR
- [ ] Three consecutive full runs: green and **identical**
- [ ] `node --check` passes on every file in `static/js/`
- [ ] `pip-audit --strict --no-deps` exits 0
- [ ] `pip install -r requirements.lock` succeeds on Linux **and** Windows
- [ ] Dependabot PRs show real check results, not "skipped"
- [ ] Branch protection requires all four checks on `main`

## Risk notes

- **1.5 (`pull_request_target`)** is the one security-sensitive change here. That trigger runs with a **write-capable token on the base ref**; never check out and execute PR head code under it. Preferring plain `pull_request` for Dependabot avoids the issue entirely — recommended.
- **2.6 / Python 3.14** — don't merge the Dockerfile bump on Dependabot's word. README states 3.11+; the app was verified here on **3.11.2**. Test 3.12→3.14 explicitly first.
- **2.4 lock regeneration** may pull in newer transitive deps and surface fresh test failures — do it *after* Phase 3, or budget for churn.
- **5.1 history rewrite** — untracking is safe; `git filter-repo` breaks every fork and clone. Recommend untrack-only unless clone size becomes a real complaint.
